## PART 1: DOCKER INTERVIEW QUESTIONS

### 1A. Docker Beginner 

#### Q1: Can you explain the difference between a Docker Image and a Docker Container?
**1. Interviewer intention:** Testing fundamental understanding of Docker architecture. Do you know the difference between state and definition?
**2. Complete answer:** A Docker image is a read-only template that contains a set of instructions for creating a Docker container. It includes the application code, libraries, dependencies, and tools required to run the application. It represents the application at rest. A Docker container, on the other hand, is a running instance of an image. It is the application in motion. When you start a container from an image, Docker adds a read-write layer (the container layer) on top of the read-only image layers, allowing the container to make changes to its filesystem without affecting the underlying image.
**3. What a wrong/weak answer looks like:** "An image is like a virtual machine ISO and a container is the running virtual machine." (Too much comparison to VMs, misses the layer architecture).
**4. Follow-up questions:** How do you reduce the size of an image? Where are images stored locally?
**5. Production example:** In a CI/CD pipeline, the CI server builds the image (e.g., `myapp:v1.2`) and pushes it to a registry. The production server pulls this image and runs it as a container to serve traffic.
**6. Commands/YAML:** 
```bash
docker build -t myapp:v1.2 . # Creates image
docker run -d myapp:v1.2     # Creates container
```
**7. STAR method:** (Not heavily applicable to fundamental trivia, but useful if asked "Tell me about a time you had to optimize this.")

#### Q2: What are Docker volumes and why are they used instead of bind mounts in production?
**1. Interviewer intention:** Evaluating knowledge of container storage persistence and best practices.
**2. Complete answer:** Docker containers are ephemeral; any data written to their writable layer is lost when the container is removed. Volumes are the preferred mechanism for persisting data generated by and used by Docker containers. Volumes are fully managed by Docker (stored in `/var/lib/docker/volumes/` on Linux) and are isolated from the core functionality of the host machine. We prefer volumes over bind mounts in production because volumes are easier to back up or migrate, you can manage them using Docker CLI commands, they work on both Windows and Linux containers, and volume drivers allow you to store volumes on remote hosts or cloud providers. Bind mounts are dependent on the host machine's directory structure and OS, which creates tight coupling and security risks if a container mounts a sensitive host directory.
**3. What a wrong/weak answer looks like:** "Volumes are just folders on the host that map to the container." (Confuses volumes with bind mounts, fails to highlight Docker's management).
**4. Follow-up questions:** How do you clean up unused volumes? What is a volume driver?
**5. Production example:** Running a PostgreSQL database in a container. The database files in `/var/lib/postgresql/data` must be mapped to a Docker volume so that if the container restarts or is upgraded, the data persists.
**6. Commands/YAML:** 
```yaml
services:
  db:
    image: postgres:13
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```
**7. STAR method:** N/A

#### Q3: What is the purpose of a Dockerfile? Mention some key instructions.
**1. Interviewer intention:** Checking basic image building knowledge and syntax.
**2. Complete answer:** A Dockerfile is a text document containing all the commands a user could call on the command line to assemble an image. It automates the image creation process. Key instructions include `FROM` (sets the base image, must be the first instruction), `WORKDIR` (sets the working directory for subsequent instructions), `COPY` (copies files/directories from the host to the container), `RUN` (executes commands in a new layer and commits the results, used for installing packages), `ENV` (sets environment variables), `EXPOSE` (documents which ports the application listens on), and `CMD` or `ENTRYPOINT` (specifies the default command to execute when the container starts).
**3. What a wrong/weak answer looks like:** Confusing `RUN` (runs during build) with `CMD` (runs during container start).
**4. Follow-up questions:** What is the difference between `COPY` and `ADD`? What is the difference between `CMD` and `ENTRYPOINT`?
**5. Production example:** Building a Node.js microservice image.
**6. Commands/YAML:** 
```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
CMD ["node", "server.js"]
```
**7. STAR method:** N/A

### 1B. Docker Intermediate

#### Q1: Explain Docker's OverlayFS and the Copy-on-Write (CoW) strategy.
**1. Interviewer intention:** Testing deep knowledge of Docker's storage drivers and how layers actually work under the hood.
**2. Complete answer:** Docker uses storage drivers like OverlayFS (specifically overlay2) to manage image and container layers. An image consists of multiple read-only layers. When a container is launched, Docker adds a thin, writable "container layer" on top. The Copy-on-Write (CoW) strategy dictates that if a container needs to modify a file that exists in a lower read-only layer, OverlayFS copies the file up into the writable container layer, and the modification happens there. The lower layer remains untouched. This sharing of read-only layers drastically reduces disk space usage and speeds up container startup. However, extensive CoW operations (like writing many small files or database transactions) can incur a performance penalty.
**3. What a wrong/weak answer looks like:** Saying "Docker copies the whole image to start a container."
**4. Follow-up questions:** Why shouldn't you run a database directly in a container layer? (Because CoW performance is poor for high-I/O workloads, hence volumes).
**5. Production example:** Realizing that a containerized application performing heavy logging to its local filesystem (instead of a volume or stdout) was experiencing disk I/O bottlenecks due to constant CoW overhead.
**6. Commands/YAML:** `docker info | grep "Storage Driver"`
**7. STAR method:** 
- **S:** We had a legacy app logging directly to a file inside the container.
- **T:** Performance degraded under load, and container sizes ballooned.
- **A:** I identified CoW overhead as the bottleneck, redirected logs to stdout, and used a Docker logging driver.
- **R:** Disk I/O dropped by 40% and container sizes stabilized.

#### Q2: How do multi-stage builds work, and why are they crucial?
**1. Interviewer intention:** Assessing understanding of image optimization and security.
**2. Complete answer:** Multi-stage builds allow you to use multiple `FROM` statements in a single Dockerfile. Each `FROM` instruction begins a new stage of the build. You can selectively copy artifacts from one stage to another, leaving behind everything you don't need in the final image. This is crucial for compiled languages like Go, Java, or C++. In the first stage, you include all build tools, SDKs, and source code to compile the binary. In the final stage, you start from a minimal base image (like `alpine` or `scratch`) and only copy the compiled binary. This drastically reduces the final image size (improving pull times and cost) and minimizes the attack surface by removing build tools and unnecessary libraries from production.
**3. What a wrong/weak answer looks like:** Mentioning it makes builds faster (it usually doesn't, it makes images *smaller*).
**4. Follow-up questions:** What is a distroless image? How do you copy from a specific stage?
**5. Production example:** A Go microservice where the build stage is 800MB (golang base image + source), but the final production stage is 15MB (scratch image + compiled binary).
**6. Commands/YAML:** 
```dockerfile
# Stage 1: Build
FROM golang:1.20 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp main.go

# Stage 2: Final
FROM alpine:3.18
WORKDIR /root/
COPY --from=builder /app/myapp .
CMD ["./myapp"]
```

### 1C. Docker Advanced

#### Q1: What is the relationship between Docker, containerd, and runc? (The OCI Spec)
**1. Interviewer intention:** Do you understand modern container architecture, or do you just know the `docker` CLI?
**2. Complete answer:** Docker is no longer a monolithic architecture. It is broken down into modular components complying with the Open Container Initiative (OCI). 
- **runc:** This is the low-level container runtime. It interfaces directly with the Linux kernel (cgroups, namespaces) to actually spawn and run containers.
- **containerd:** This is the high-level container runtime. It manages the complete container lifecycle of its host system, from image transfer and storage to container execution and supervision. It orchestrates `runc`.
- **dockerd (Docker Daemon):** This is the higher-level engine that provides the API, manages volumes, networks, and builds. When you run a container, the Docker CLI talks to dockerd, which talks to containerd, which uses runc to spawn the process. This decoupling means containerd can be updated without restarting containers (which runc handles).
**3. What a wrong/weak answer looks like:** "Docker is the hypervisor for containers."
**4. Follow-up questions:** Why did Kubernetes deprecate dockershim in favor of containerd?
**5. Production example:** Debugging container startup issues by bypassing Docker and looking at containerd logs using `ctr` or `crictl`.

#### Q2: How would you secure a Docker environment from a container breakout?
**1. Interviewer intention:** Evaluating advanced security posture and knowledge of kernel isolation.
**2. Complete answer:** A defense-in-depth approach is required. 
1. **Rootless Docker:** Run the Docker daemon as a non-root user.
2. **User Namespaces:** Map the root user inside the container to a non-privileged user on the host.
3. **Capabilities:** Drop all capabilities (`--cap-drop=all`) and add back only what is necessary (e.g., `NET_BIND_SERVICE`).
4. **Seccomp/AppArmor:** Use default or custom profiles to restrict which system calls the container can make to the host kernel.
5. **No Privileged Mode:** Never run `--privileged` unless absolutely necessary (it grants almost full access to the host).
6. **Read-only Root Filesystem:** Run containers with `--read-only` to prevent attackers from dropping malware into the container layer.
**3. What a wrong/weak answer looks like:** "Just don't expose port 22 on the container."
**4. Follow-up questions:** What is the difference between dropping privileges and rootless Docker?

### 1D. Docker Scenario-Based

#### Q1: A container keeps restarting with Exit Code 137. How do you troubleshoot and fix it?
**1. Interviewer intention:** Testing troubleshooting methodology and knowledge of exit codes.
**2. Complete answer:** Exit code 137 indicates that the container was terminated by a `SIGKILL` (128 + 9). In a container environment, this almost always means the container was OOMKilled (Out Of Memory) by the host's kernel or the orchestrator because it exceeded its memory limit. 
First, I would inspect the container logs and events using `docker inspect` to verify the OOM status (`"OOMKilled": true`). Then, I would look at host metrics (`dmesg -T | grep -i oom`) to see the kernel killer logs. 
To fix it, I have two paths: 
1. **Application Optimization:** Profile the application for memory leaks (e.g., heap dumps in Java, memory profiling in Node).
2. **Resource Adjustment:** If the application legitimately needs more memory, increase the memory limit (`docker run -m 2g`).
**3. What a wrong/weak answer looks like:** "It's a permission denied error, run as root." (137 is specifically SIGKILL).
**5. Production example:** A Java Spring Boot application in a container with a 512MB limit. The JVM didn't know about container limits and allocated a larger heap, leading to constant OOMKilled events. Fixed by passing `-XX:MaxRAMPercentage` to the JVM.

#### Q2: You need to deploy a Docker Compose stack with zero downtime, but you cannot use Kubernetes/Swarm. How?
**1. Interviewer intention:** Can you engineer solutions within constraints? Do you understand blue/green or rolling concepts at a raw level?
**2. Complete answer:** While Compose isn't designed for orchestrating zero-downtime deployments natively, we can achieve it using a reverse proxy (like Nginx, Traefik, or HAProxy) and multiple service definitions.
1. Define two identical services in `docker-compose.yml` (e.g., `web-blue` and `web-green`).
2. Have Nginx route traffic to `web-blue`.
3. To deploy, bring up `web-green` with the new image.
4. Run health checks against `web-green` manually or via a script.
5. If healthy, reload the Nginx configuration to point to `web-green`.
6. Tear down `web-blue`.
Alternatively, using `docker-compose up -d --scale web=2 --no-recreate` combined with a dynamic reverse proxy like Traefik that auto-discovers containers via Docker socket can achieve rolling updates by gracefully replacing instances one by one.

## PART 2: AWS INTERVIEW QUESTIONS

### 2A. AWS Beginner

#### Q1: What is a VPC and what are its core components?
**1. Interviewer intention:** Core networking fundamentals in AWS.
**2. Complete answer:** A Virtual Private Cloud (VPC) is a logically isolated network in the AWS cloud where you launch your AWS resources. It resembles a traditional on-premises network but with the scalability of AWS. Core components include:
- **Subnets:** Segments of the VPC IP address range in specific Availability Zones. They can be public (route to IGW) or private.
- **Route Tables:** A set of rules determining where network traffic from subnets is directed.
- **Internet Gateway (IGW):** Allows communication between instances in your VPC and the internet.
- **NAT Gateway:** Allows instances in a private subnet to connect to the internet (for updates) while preventing internet sources from initiating a connection to those instances.
- **Security Groups:** Stateful virtual firewalls operating at the instance/ENI level.
- **Network ACLs:** Stateless virtual firewalls operating at the subnet level.
**3. What a wrong/weak answer looks like:** Failing to distinguish between Security Groups and NACLs, or not knowing how a subnet becomes "public."
**5. Production example:** Creating a 3-tier architecture: public subnets for Application Load Balancers, private subnets for EC2 application servers, and isolated database subnets for RDS.

#### Q2: Explain the difference between Security Groups and Network ACLs.
**1. Interviewer intention:** Security fundamentals and statefulness vs statelessness.
**2. Complete answer:** Both are virtual firewalls, but they operate differently. 
- **Scope:** SGs operate at the instance/Elastic Network Interface (ENI) level. NACLs operate at the Subnet level.
- **Statefulness:** SGs are stateful; if you allow incoming traffic on port 443, the return traffic is automatically allowed regardless of outbound rules. NACLs are stateless; you must explicitly allow both inbound and outbound traffic.
- **Rules:** SGs only support ALLOW rules. NACLs support both ALLOW and DENY rules, evaluated in number order (lowest to highest).
- **Default behavior:** By default, new SGs deny all inbound and allow all outbound traffic. Default NACLs allow all inbound and outbound traffic.
**3. What a wrong/weak answer looks like:** Misunderstanding stateful vs. stateless.

### 2B. AWS Intermediate

#### Q1: Explain IAM Policy Evaluation Logic (How AWS decides to Allow or Deny).
**1. Interviewer intention:** Do you understand complex security boundaries?
**2. Complete answer:** AWS evaluates policies across multiple layers: Service Control Policies (SCPs), Resource-based policies, Identity-based policies, IAM boundaries, and Session policies.
The core logic evaluates all applicable policies and follows these rules:
1. **Default Deny:** By default, all requests are denied.
2. **Explicit Deny:** If ANY applicable policy includes an explicit `Deny`, the request is denied. Explicit Deny ALWAYS trumps Allow.
3. **Explicit Allow:** If no explicit Deny exists, and there is an explicit `Allow` in an applicable policy, the request is allowed.
For example, if an IAM user has `s3:*` allow policy, but an SCP on the AWS Organization denies `s3:DeleteBucket`, the user cannot delete a bucket because the explicit deny from the SCP overrides the allow.

#### Q2: You have EC2 instances in a private subnet that need to download updates from the internet. How do you architect this securely?
**1. Interviewer intention:** VPC architecture, NAT Gateway, and traffic routing.
**2. Complete answer:** The instances are in a private subnet, meaning they don't have public IPs and their route table does not have a route to an Internet Gateway (IGW). To allow outbound internet access for updates:
1. Provision a NAT Gateway (Network Address Translation) in a **Public Subnet** within the same VPC. (Alternatively, a NAT Instance for cost savings, but NAT Gateway is managed and highly available).
2. The NAT Gateway must have an Elastic IP attached.
3. Update the Route Table associated with the **Private Subnet** to point destination `0.0.0.0/0` (internet bound traffic) to the NAT Gateway ID as the target.
This allows the EC2 instances to initiate outbound requests, but prevents the internet from initiating inbound requests to the instances.

### 2C. AWS Advanced

#### Q1: Explain the AWS STS AssumeRole workflow and when you would use cross-account roles.
**1. Interviewer intention:** Deep understanding of identity federation, temporary credentials, and multi-account strategies.
**2. Complete answer:** AWS Security Token Service (STS) allows you to request temporary, limited-privilege credentials. `AssumeRole` is the API call used to acquire these credentials.
The flow works like this: Principal A (e.g., an IAM User in Account 1) makes an `sts:AssumeRole` API call requesting to assume Role B (in Account 2). 
For this to work:
1. Principal A must have an identity policy allowing `sts:AssumeRole` on Role B's ARN.
2. Role B must have a Trust Policy (Resource-based policy) that lists Principal A's account as a trusted entity.
If both conditions are met, STS returns temporary credentials (Access Key, Secret Key, and Session Token) valid for a short duration (15 mins to 12 hours).
This is heavily used in AWS Organizations for Centralized Identity (e.g., SSO into a central account, assuming roles in dev/prod accounts) or granting a 3rd-party vendor access to your AWS resources securely without creating static IAM users.

#### Q2: What is the difference between a VPC Gateway Endpoint and an Interface Endpoint (PrivateLink)?
**1. Interviewer intention:** Advanced networking and private AWS service access.
**2. Complete answer:** Both allow VPC resources to access AWS services privately without routing traffic over the public internet, avoiding NAT Gateways and IGWs.
- **Gateway Endpoints:** Only support Amazon S3 and DynamoDB. They work by adding a prefix-list route to your VPC Route Table. They are completely free. Traffic leaves your subnet, hits the VPC router, and goes directly to S3/DynamoDB.
- **Interface Endpoints (AWS PrivateLink):** Supports almost all other AWS services (EC2 API, Kinesis, SNS, API Gateway, etc.) and your own custom endpoint services. It provisions an Elastic Network Interface (ENI) with a private IP directly inside your subnet. Traffic is sent to this private IP. These endpoints have an hourly cost plus data processing fees.

### 2D. AWS Scenario-Based

#### Q1: An Application Load Balancer (ALB) is returning 502 Bad Gateway errors for some requests. How do you investigate?
**1. Interviewer intention:** Real-world incident response and understanding of ALB mechanics.
**2. Complete answer:** A 502 Bad Gateway from an ALB means the load balancer was able to connect to the target, but the target returned an invalid or malformed response, or closed the connection unexpectedly.
My investigation steps:
1. **Check ALB Access Logs:** Query logs in Athena to find exactly which target IP returned the 502 and the request details.
2. **Check Target Health:** Ensure EC2/ECS targets are healthy in the target group.
3. **Connection timeouts:** The most common cause is the Keep-Alive timeout on the backend application (e.g., Node.js, Tomcat) is *shorter* than the ALB's Idle Timeout (default 60 seconds). If the app closes the connection while the ALB is still trying to send data, a 502 occurs. I would increase the app's keep-alive timeout to > 60s.
4. **Application Logs:** Check the specific backend instance logs for crashes, OOM errors, or unhandled exceptions that caused the web server process to terminate abruptly.

#### Q2: Your monthly AWS bill doubled suddenly. You are tasked with finding out why. What is your approach?
**1. Interviewer intention:** FinOps awareness and use of AWS billing tools.
**2. Complete answer:** I would take a systematic approach using AWS Cost Management tools:
1. **AWS Cost Explorer:** This is the first stop. I would group costs by `Service` and filter by the last 30 vs 60 days to identify exactly which service caused the spike. 
2. **Group by Usage Type/Resource:** Once the service is identified (e.g., EC2), I would group by `Usage Type` (is it compute hours, Data Transfer Out, NAT Gateway bytes?) to narrow it down.
3. **AWS Cost Anomaly Detection:** Check if there are any triggered alerts giving context.
4. **CloudTrail / Config:** If the spike is due to new resources (e.g., a huge Redshift cluster was spun up), I would use CloudTrail to see *who* made the API call to create it.
5. **Common Culprits:** I'd look for unattached EBS volumes, forgotten NAT Gateways, massive S3 data transfer out, or unoptimized CloudWatch logs ingestion.

## PART 3: TERRAFORM INTERVIEW QUESTIONS

### 3A. Terraform Beginner

#### Q1: What is Terraform State and why is it important?
**1. Interviewer intention:** Core Terraform concepts.
**2. Complete answer:** Terraform state is a JSON file (`terraform.tfstate`) that maps the resources defined in your Terraform configuration files (.tf) to the actual real-world infrastructure objects provisioned in the cloud provider. It serves as Terraform's database. 
It is important because:
- **Performance:** It caches resource attributes, so Terraform doesn't have to query the provider API for every single resource on every plan.
- **Tracking metadata:** It tracks resource dependencies and metadata (like resource IDs) that are not visible in the config.
- **Detecting Drift:** When you run `terraform plan`, Terraform compares your config against the state, and the state against the real world, to determine what needs to be created, updated, or destroyed.
**3. What a wrong/weak answer looks like:** "It's just a backup of your code."
**4. Follow-up questions:** Should you commit state to git? (No, use remote state).

#### Q2: Explain Terraform `init`, `plan`, and `apply`.
**1. Interviewer intention:** Workflow knowledge.
**2. Complete answer:** 
- `terraform init`: Initializes a working directory containing Terraform configuration. It downloads the required provider plugins (e.g., AWS, GCP) and configures the backend for state storage.
- `terraform plan`: Reads the code and the current state, and outputs an execution plan. It tells you exactly what Terraform *will* do (add, change, destroy) without actually provisioning anything. It's a dry run.
- `terraform apply`: Executes the actions proposed in the Terraform plan. It makes the API calls to the cloud provider to provision or modify infrastructure and updates the state file upon success.

### 3B. Terraform Intermediate

#### Q1: Why should you use a Remote Backend (like S3 + DynamoDB) instead of local state?
**1. Interviewer intention:** Collaboration and state management best practices.
**2. Complete answer:** Storing state locally (`terraform.tfstate` on your laptop) is fine for personal testing, but disastrous for teams. 
We use a remote backend like AWS S3 combined with a DynamoDB table for two main reasons:
1. **Centralized Storage & Security:** The state file contains sensitive data (passwords, private IPs, database endpoints) in plain text. S3 allows us to encrypt the state at rest (KMS) and restrict access via IAM. It also ensures all team members and CI/CD pipelines use the exact same state file.
2. **State Locking:** If two engineers run `terraform apply` simultaneously, they will corrupt the state and the infrastructure. DynamoDB provides state locking; when Engineer A runs a plan/apply, a lock is acquired in the DynamoDB table. If Engineer B runs a command, Terraform fails immediately, stating the state is locked.
**6. Commands/YAML:**
```hcl
terraform {
  backend "s3" {
    bucket         = "my-tf-state-bucket"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-lock"
    encrypt        = true
  }
}
```

#### Q2: What is the difference between `count` and `for_each`?
**1. Interviewer intention:** Meta-argument usage and understanding of resource indexing.
**2. Complete answer:** Both allow you to create multiple instances of a resource, but they handle indexing differently.
- `count` takes a whole number and creates that many resources. The resources are indexed as a list (e.g., `aws_instance.server[0]`, `[1]`). If you remove an item from the middle of the list, Terraform's index shifts, causing it to unnecessarily destroy and recreate all subsequent resources.
- `for_each` takes a map or a set of strings. Resources are indexed by the map key or string value (e.g., `aws_instance.server["web1"]`). This is much safer. If you remove an item, Terraform only destroys that specific resource identified by its key, without affecting the others.
Generally, `for_each` is preferred unless you are creating truly identical, disposable resources.

### 3C. Terraform Advanced

#### Q1: Someone manually deleted a critical EC2 instance via the AWS Console that was managed by Terraform. What happens on the next `terraform plan` and how do you fix it?
**1. Interviewer intention:** Drift detection and state reconciliation.
**2. Complete answer:** When you run `terraform plan`, Terraform performs a refresh phase (unless disabled). It queries the AWS API for all resources in the state file. It will notice the EC2 instance no longer exists in reality. 
The plan output will show that Terraform intends to **create** the EC2 instance to match the configuration files (since the code still says the instance should exist). 
To fix it, assuming we want the instance back, you simply run `terraform apply`. Terraform will provision a new instance and update the state with the new instance ID. 
If the manual deletion was intentional and you want to keep it deleted, you must remove the resource block from your `.tf` files and then run `terraform apply` to align the state.

#### Q2: How do you refactor Terraform code (e.g., move a resource into a module) without Terraform destroying and recreating the infrastructure?
**1. Interviewer intention:** State surgery and advanced state management (`moved` blocks).
**2. Complete answer:** Historically, we had to use CLI state surgery commands like `terraform state mv` to rename resources in the state file to match the new code structure.
Since Terraform 1.1, the best practice is to use declarative `moved` blocks. 
If I wrap an existing `aws_instance.web` into a module called `web_server`, I would update my `.tf` code to call the module, and add a block:
```hcl
moved {
  from = aws_instance.web
  to   = module.web_server.aws_instance.this
}
```
When `terraform plan` runs, Terraform reads the `moved` block, updates the address of the resource in the state file internally, and reports that no infrastructure changes are required. The state is cleanly updated without downtime.

## PART 4: COMPLETE INTERVIEW CHEAT SHEET

### Top 10 Most Common Interview Mistakes
1. **Docker:** Confusing images with containers in conversation.
2. **Docker:** Recommending `--privileged` mode as a solution to permission issues.
3. **Docker:** Not knowing the difference between CMD and ENTRYPOINT.
4. **AWS:** Overusing NAT Gateways when VPC Endpoints would be cheaper/more secure.
5. **AWS:** Recommending IAM Users instead of IAM Roles for EC2/ECS/EKS instances.
6. **AWS:** Forgetting that Security Groups are stateful and NACLs are stateless.
7. **Terraform:** Recommending committing `terraform.tfstate` to Git.
8. **Terraform:** Using `count` instead of `for_each` for complex resource maps.
9. **Terraform:** Recommending manual state file JSON editing to fix issues.
10. **General:** Not admitting "I don't know" and trying to guess an architecture.

### STAR Method Templates for DevOps Behavioral Questions
**Scenario: Tell me about a time you reduced costs.**
- **Situation:** Our AWS bill was growing 20% month-over-month.
- **Task:** I was tasked with auditing and reducing infrastructure spend without impacting performance.
- **Action:** I implemented a tagging strategy using Terraform, identified idle development RDS instances, moved them to Aurora Serverless, and migrated our non-critical EC2 workloads to Spot Instances using ASGs.
- **Result:** We reduced our monthly AWS spend by 35% ($10k/month).

**Scenario: Tell me about a time you handled a production incident.**
- **Situation:** Production API was returning 504 Gateway Timeouts.
- **Task:** Act as Incident Commander to restore service.
- **Action:** Checked Datadog metrics, identified the RDS database CPU was pinned at 100%. Found a missing index on a new deployed query. Rolled back the deployment via our CI/CD pipeline while the DBA added the index concurrently. 
- **Result:** Service restored in 15 minutes, implemented a new automated database query review step in CI.
