# Chapter 8: Log Analysis

## 8.1 Why Logs Matter
When an application crashes, a network connection drops, or a deploy fails, **logs are the source of truth**. 

Let's use a real-world analogy:
> **Analogy:** Think of an operating system or application server as an airplane. 
> * **Monitoring metrics** (CPU, RAM, network bandwidth) are the dashboard indicators showing speed, altitude, and fuel level. They tell you *that* the plane is dropping altitude.
> * **Logs** are the **Black Box flight recorder**. They record every mechanical action, voice conversation, and switch toggle in chronological order. They tell you *why* the plane is dropping altitude (e.g., "Fuel pump valve failed to open at 08:00:05").

Without logging, diagnosing system state is guesswork. DevOps Engineers must be experts at finding, filtering, and diagnosing logs to identify root causes of failures.

---

## 8.2 Log Types

1. **System Logs:** Record events relating to the operating system kernel, service startups, hardware states, and background system daemons.
2. **Application Logs:** Generated by running applications (e.g., Java, Node.js, Python apps). They contain custom developer events, SQL queries, errors, and warning statements.
3. **Security Logs:** Record access control events, logins, sudo execution, and authorization failures.
4. **Access Logs:** Generated by web servers and load balancers (e.g., Nginx, Apache, AWS ALB) detailing every incoming HTTP request client IP, URL, and status response.
5. **Audit Logs:** Track user activity and configuration changes made by system administrators or automation agents (e.g., tracking who created a Kubernetes namespace or edited a database record).

## 8.3 Linux Log Directory (`/var/log`)
Most logs in Linux are stored in `/var/log`.

```
/var/log/
├── syslog (Central system events repository)
├── auth.log (Authentication logs: logins, sudo trials)
├── kern.log (Kernel-level alerts and hardware errors)
├── boot.log (System startup service initializations)
├── dmesg (Kernel ring buffer diagnostics)
├── nginx/
│   ├── access.log (Incoming HTTP requests)
│   └── error.log (Web server errors and upstream crashes)
└── mysql/
    └── error.log (Database startup and query errors)
```

### Log File Breakdown:
* **`/var/log/syslog` (or `/var/log/messages` on RHEL):** The central log file for general system activity.
* **`/var/log/auth.log` (or `/var/log/secure` on RHEL):** Crucial for auditing security events. Tracks successful and failed logins, SSH connections, and privilege escalation commands (`sudo`).
* **`/var/log/kern.log`:** Captures kernel messages. Useful for debugging hardware errors, firewall blocks, and Out-of-Memory (OOM) killer terminations.
* **`dmesg` Command:** Reads the kernel ring buffer directly. Used to debug device driver attachments during system boot before `/var/log` is writable.

## 8.4 Log Investigation Commands

### 1. `tail` (Real-time tracking)
* **Syntax:** `tail -f <file>` (Follow) or `tail -n <lines> <file>`.
* **Example:**
  ```bash
  tail -n 50 -f /var/log/nginx/access.log
  ```

### 2. `less` (Large log navigation)
* **Syntax:** `less <file>`. Run search inside `less` by typing `/pattern` and pressing `n` for next occurrences.

### 3. `grep` (Filter logs matching pattern)
* **Syntax:** `grep "ERROR" /var/log/syslog`
* **Example:** Find authentication failures:
  ```bash
  grep "Failed password" /var/log/auth.log
  ```
  *Expected Output:*
  ```text
  Jun  1 08:12:05 web-prod sshd[1234]: Failed password for invalid user root from 198.51.100.42 port 49512 ssh2
  ```

---

### 4. `journalctl` (Systemd Journal Parser)
Modern Linux distros use `systemd` to manage services. Systemd stores logs in a secure, binary format called the **Journal**. Use `journalctl` to read these logs.

* **Command Options:**
  * `journalctl -u <service>` (Show logs for a specific systemd unit).
  * `journalctl -f` (Follow new incoming logs).
  * `journalctl -n <lines>` (Show last N lines).
  * `journalctl --since "1 hour ago"` (Time-based filtering).
  * `journalctl -p err` (Filter by severity: emergency, alert, critical, error).
* **Example:** Inspecting failed Nginx services:
  ```bash
  journalctl -u nginx --since "30 minutes ago"
  ```
  *Expected Output:*
  ```text
  -- Journal begins at Mon 2026-06-01 03:00:00 UTC. --
  Jun 01 09:00:01 web-prod systemd[1]: Starting A high performance web server and a reverse proxy server...
  Jun 01 09:00:02 web-prod nginx[4502]: nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
  Jun 01 09:00:02 web-prod systemd[1]: nginx.service: Control process exited, code=exited, status=1/FAILURE
  ```

## 8.5 Production Incident Root Cause Analysis (RCA)

### Incident 1: Application Crashed (OOM Killer)
* **Symptom:** Your Python/Java web application stops responding. Running `systemctl status` shows code `killed`.
* **Investigation:**
  Run grep on syslog searching for kernel OOM messages:
  ```bash
  grep -i "oom" /var/log/syslog || dmesg | grep -i "oom-killer"
  ```
* **Expected Output:**
  ```text
  Jun  1 09:12:03 srv-prod kernel: [12042.85] python3 invoked oom-killer: gfp_mask=0x100cca(GFP_HIGHUSER_MOVABLE), order=0, oom_score_adj=0
  Jun  1 09:12:03 srv-prod kernel: [12042.85] Out of memory: Killed process 15024 (python3) total-vm:4194304kB, anon-rss:2097152kB, file-rss:0kB, shmem-rss:0kB
  ```
* **Root Cause:** The system ran completely out of physical RAM. The Linux kernel invoked the **OOM (Out-of-Memory) Killer** to save the operating system from freezing, selecting and terminating the largest memory consumer (`python3`, PID 15024).

---

### Incident 2: Database Connection Refused
* **Symptom:** Users see "500 Internal Server Error" on your website. Application logs show `Database connection refused`.
* **Investigation:**
  1. Inspect PostgreSQL or MySQL logs inside `/var/log/postgresql/` or `/var/log/mysql/`.
  2. Let's inspect PostgreSQL logs:
     ```bash
     tail -n 20 /var/log/postgresql/postgresql-14-main.log
     ```
* **Expected Output:**
  ```text
  2026-06-01 09:15:02 UTC FATAL:  password authentication failed for user "app_user"
  2026-06-01 09:15:02 UTC FATAL:  no pg_hba.conf entry for host "10.0.1.25", user "app_user", database "prod_db", SSL off
  ```
* **Root Cause:**
  * The application is presenting the wrong database password, or
  * The database host configuration file `/etc/postgresql/14/main/pg_hba.conf` is missing a permission entry allowing connections from the application server's IP (`10.0.1.25`).

## 8.6 Chapter 8 Summary
* Logs document chronological system events.
* System configurations and log file targets reside in `/var/log`.
* `systemd` stores binary logs accessible via the `journalctl` utility.
* Incidents are resolved by finding error records (`grep`, `tail`) and identifying the root cause.

## 8.7 Interview Questions
1. **Q: Where would you check if you suspect a hardware failure or kernel panic occurred?**
   * *A:* Look inside `/var/log/kern.log` and run the `dmesg` command to analyze kernel-level alerts and hardware device connectivity failures.
2. **Q: How can you search for a specific error in real-time as it occurs?**
   * *A:* Pipe the follow output of a log file into grep: `tail -f /var/log/nginx/error.log | grep --line-buffered "critical"`.
3. **Q: What does the OOM Killer do in Linux?**
   * *A:* When system memory is depleted, the Out-Of-Memory Killer terminates processes (usually the one utilizing the most RAM) to prevent a system-wide kernel panic or freeze.
